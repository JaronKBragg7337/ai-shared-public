## 2. The hourly tuner: keep, and tighten

It has done nothing, which was the right thing. 169 calls, 169 holds, 0 changes, about 260,000 tokens. Fund and twin
are identical to the cent, so there is no evidence either way. It held through a sleeve falling 7.5% in a week and
said why (too little data). The 6-month rule stands; first real decision is about mid-May 2027.

Tighten one thing (change 3): the tuner is asked 24 times a day about numbers that change at most twice a day. Every
figure it sees comes from daily closes. Asking the same question 24 times cannot add information; it only adds 24
chances a day for a random "change" to slip through, and a cut can be made any hour. The tuner's own rule says churn
makes it lose to the twin.

This touches Jaron's words ("every hour make a judgement call"). The hourly run, data checks, risk rules and dashboard
line all stay hourly. Only the paid AI call waits for something new.

## 3. Proposed changes

### Change 1 - fix the stale backtest (bug, run.py)
- **Exact change:** `run_backtest` reuses the saved file when `through_etf` and `cfg_hash` match. Add the last crypto
  day to that test: pass `fresh.get("BTC-USD")` in, store it as `through_crypto`, and require it to match too.
  Also add a hash of `engine.py` to the key, so a code change can never be answered from an old saved backtest.
- **Evidence:** A session can only be booked once that day's crypto bar is finished (00:00 UTC). But the saved file gets
  its "current" stamp at 21:17 UTC, three hours earlier, so it is stamped current while still missing that session,
  and never redone. `backtest.json` says through 11/20 but covers 686 days = ends 11/19. Re-run ending 11/19: +6.561%/yr,
  an exact match to the file. Re-run through 11/21: fund +5.83%, SPY +9.9% (file says +12.1%), 60/40 +7.6% (file +8.7%).
- **Risk of fooling ourselves:** none; it only makes the number current. It will look worse. That is the point.
- **Check after:** delete `state/ai-fund/backtest.json`, run once. Backtest "days" must equal the days from 2025-01-02
  to the fund's last booked date. Today that should read +5.8%/yr and $486/month. Twin untouched.
- **Until this is in, any "re-run the backtest" check can silently return old numbers. Delete the file first.**

### Change 2 - the verdict clock counts weekends (bug vs the design, run.py)
- **Exact change:** in `build_summary`, `days = len(b["eq"])` counts every calendar day, including weekends and the
  three days before anything was bought. Replace with a count of finished SPY sessions since the build:
  `sess = {x["date"] for x in series["SPY"]["bars"] if x["t"] >= st["not_before"] and D.bar_complete(x, "SPY", now_ts)}`
  then `days = sum(1 for e in b["eq"] if e[0] in sess)`. One clock for all six sleeves, crypto included.
- **Evidence:** the dashboard says "9 of 126 days" after 5 sessions. DESIGN.md says 126 *trading* days. As coded, every
  sleeve gets its verdict about 2027-03-18; by the design it should be about 2027-05-18. Two months too early.
- **Risk of fooling ourselves:** none; it makes the test stricter. Do it now while there is no result to be tempted by.
- **Check after:** SUMMARY.md should read "5 of 126 days" until Monday's close is booked. Fund, twin and backtest values
  must not move by a cent (this only changes a label).

### Change 3 - call the tuner only when there is something new (tuner.py)
- **Exact change:** in `hourly()`, build the compact state, drop `"now"`, hash it. If the hash equals the one stored on
  the last record that made a call, skip the AI call and log
  `{"called": false, "decision": "hold", "note": "nothing new since <time>; last judgement stands", "sig": <hash>}`.
  Store `sig` on every record that does call. New closes, a data flag, a risk event or a config change all change the
  hash and trigger a real call.
- **Evidence:** section 2. 169 identical answers; inputs come only from daily closes.
- **Risk of fooling ourselves:** this is not a hindsight change, it uses no price history. The real risk is the other
  way: we give up a good idea the model might have had on its 15th look at the same numbers. That is noise we want gone.
- **Check after:** next week's tuner log should show about 2 real calls a day (1 on weekend days), roughly 20-25k tokens
  instead of 260k. The twin is unaffected by construction.

## 5. What the builders missed

1. **Idle cash earns nothing, and dipbuy is graded against T-bills.** In the backtest dipbuy is out of the market on
   77% of sessions earning 0% while its benchmark earns 3.7%. It starts about 2.9 pts/yr behind before it trades.
   I tested parking its idle cash in BIL through the paper broker, costs included: dipbuy +1.7% -> +4.0%/yr, fund
   +5.8% -> +6.1%, no gain at all at 3x costs. Not proposed this week: it raises our own numbers, so it deserves its own
   look. Decide next review. The 5% reserve has the same issue (about 0.2 pt/yr).
2. **The verdict test compares raw return against a riskier benchmark.** volcore runs at about 6% volatility against
   60/40 at 11%; quality at 10% against SPY at 17%. Such sleeves "win" in down weeks like this one and "lose" in up
   markets. The test would measure market direction, not the sleeve. Fix: compare against the benchmark mixed with
   T-bills down to the sleeve's own volatility. **Settle this by about 12/20, before there is enough data to bias the
   choice.**
3. **The twin can never be un-halted.** It reads `fund_halt_reset` from its frozen config, which is false forever. After
   any halt the fund would be restarted and the twin would sit in cash, breaking the tuner comparison. The twin should
   read that one flag from the live config. Also the flag is not one-shot: left on, it would clear the next halt
   instantly. The engine should set it back to false when it uses it. Not urgent, fix before it is needed.
4. **Two design rules are not in code.** "Retire at 12 months if P < 0.50" and "tuner off at 6 months if it has not beaten
   the twin" exist only in DESIGN.md (`verdict.retire_days` and `p_retire_below` are never read). Fine as weekly-review
   duties, but DESIGN.md says "(engine)". Either code them or change that word.
5. **No second price source for ETFs.** Crypto is cross-checked, ETFs are not. A free daily-close source alongside Yahoo
   (Stooq's CSV, if it still answers without a key) would let the hourly check catch a bad Yahoo print.
6. **The Fed-odds shadow will almost never fire.** Trigger is a 0.10 pt move in an hour; the biggest hourly move this
   week, during an 8% stock drop, was 0.0075 (range 4.23-4.26 all week). 0 shadow trades. It costs nothing, so leave it,
   but expect a handful of events a year. Do not lower the trigger after seeing which level "would have worked".
7. **"Trades 0" is misleading.** Only sells are counted. The fund holds 15 positions. Call the column "closed trades".
8. **Crypto paper fills are 17 minutes early.** Orders fill at the 00:00 UTC price but the run that decides happens at
   00:17. Small and not one-sided; no crypto trade has happened yet. Note it, fix later (fill at the live price).
9. **Heads-up, not a bug:** Thursday 11/26 is a market holiday. The engine will not book a weekday until a later session
   exists, so Thursday (crypto too) is booked about 21 hours late: Friday about 21:17 UTC instead of Thursday evening.
   The dashboard will look frozen for that stretch. A holiday list would stop that.
10. **The Codex fallback for the tuner has never worked once.** Its only try was during the DNS outage. Untested.
11. **Jaron's 11/15 direction is not in the weekly brief, so it was not done.** DESIGN.md asks this review for a broader,
    evidence-based universe (stocks + utility tokens with real usage) and two lenses (future-threat, rivals-can-both-win).
    The brief in `weekly_review.py` does not mention it. I did not fill it from memory: my knowledge stops in June 2026,
    and usage claims need today's data. It should be its own job with live sources, written as a proposal file:
    - per asset: who actually uses it, signed partners, fees/revenue, on-chain activity (free: DefiLlama, chain explorers,
      company filings), each claim with a link and a date;
    - a separate "threat exposure" score (quantum migration plan, Taiwan chip dependence, sanctions, AI substitution),
      never blended into "good now";
    - rivals scored as shared upside, tested on history (where rivals coexisted vs where one took most);
    - new names enter as $0 shadow rows first, with the entry rule written down before any price history is looked at.
